## 一、提示词工程进阶（Prompt Engineering）

### 1.1 为什么 Prompt 很重要？

同样的 AI 模型，不同的 Prompt，输出质量天差地别。

**类比：** Prompt 就像给下属布置任务——说清楚了，执行到位；说模糊了，结果跑偏。

### 1.2 基础技巧回顾

| 技巧 | 作用 | 例子 |
|------|------|------|
| **角色设定** | 让 AI 进入特定身份 | "你是一位资深产品经理..." |
| **Few-shot** | 给例子让 AI 模仿 | "请参考以下三个例子的风格..." |
| **Chain-of-Thought** | 让 AI 一步步想 | "请逐步分析：第一步...第二步..." |

### 1.3 进阶：结构化 Prompt 模板

把 Prompt 写成"填空题"，方便复用和团队协作：

```markdown
# 角色
你是一位[具体身份]，拥有[年限]年[领域]经验。

# 任务
请[具体任务描述]，目标受众是[用户群体]。

# 要求
- [要求 1：格式/风格]
- [要求 2：长度限制]
- [要求 3：禁忌事项]

# 输出格式
请以[格式]输出，包含以下部分：
1. [部分 1]
2. [部分 2]
3. [部分 3]

# 示例
输入：[例子输入]
输出：[例子输出]

# 待处理内容
输入：[实际内容]
输出：
```

**为什么结构化更好？**
- AI 对结构化内容的理解更精准
- 方便版本管理和迭代优化
- 团队协作时统一标准

### 1.4 进阶：Self-Consistency（自洽性）

对同一个问题，让 AI 回答多次，取出现频率最高的答案。

**适用场景：** 数学计算、逻辑推理、事实判断。

```
提问："以下推理是否正确？如果所有猫都怕水，且咪咪是猫，那么咪咪怕水。"

让 AI 回答 5 次，统计：
- "正确"出现 4 次
- "不正确"出现 1 次
→ 最终结论：正确（置信度 80%）
```

## 二、RAG 工程实践

### 2.1 RAG 不是万能药

当知识库及时、检索正确且模型遵循资料时，RAG 能缓解“知识过时”和“胡说八道”；它不是万能药：

| RAG 能解决的问题 | RAG 解决不了的问题 |
|-----------------|------------------|
| 知识库内容准确 | 知识库本身有错 |
| 回答有依据 | 复杂推理和创造性任务 |
| 减少幻觉 | 检索不到相关内容时仍会编 |

### 2.2 RAG 的核心挑战

#### 挑战 1：文档切分（Chunking）

**问题：** 一篇 10 页的文档，怎么切成适合检索的片段？

**切分策略对比：**

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **固定长度** | 简单、均匀 | 可能切断语义 | 通用场景 |
| **按段落** | 保留语义完整性 | 长度不均匀 | 结构化文档 |
| **按语义** | 最精准 | 计算成本高 | 高质量要求 |
| **滑动窗口** | 保留上下文 | 数据冗余 | 需要前后关联 |

**实践建议：**
- 先按段落切，每段不超过 500 字
- 代码文档按函数/类切分
- 表格数据保留表头

#### 挑战 2：检索精度

**常见问题：** 用户问"怎么退款"，检索到的却是"怎么付款"。

**优化方法：**

1. **混合检索**：关键词检索 + 向量语义检索，结果合并
2. **重排序（Re-rank）**：先用向量检索召回 50 条，再用更精准的模型排前 5
3. **查询改写**：把用户口语化的问题改写成更标准的查询

```
用户提问："我买的那个东西不想要了，能退不？"

查询改写："商品退货政策和退款流程"

→ 改写后的查询检索精度更高
```

#### 挑战 3：回答质量

**检索到了相关内容，但 AI 回答得不好。**

**优化方法：**

1. **上下文压缩**：检索到的片段太长，先压缩再传给 AI
2. **多轮检索**：第一轮检索定位文档，第二轮在该文档内精确定位
3. **引用标注**：让 AI 在回答中标注信息来源，方便验证

```
用户问："公司的年假有多少天？"

检索到片段："根据《员工手册》第三章...正式员工每年享有 15 天带薪年假..."

AI 回答："根据《员工手册》[1]，正式员工每年享有 15 天带薪年假。"

[1] 员工手册第三章第 5 条
```

### 2.3 RAG 搭建工具

| 工具 | 类型 | 特点 | 适合人群 |
|------|------|------|---------|
| **LangChain** | 开发框架 | 最流行、生态丰富、灵活 | Python/JS 开发者 |
| **LlamaIndex** | 开发框架 | 专注数据连接、RAG 能力强 | 开发者 |
| **Dify** | 低代码平台 | 可视化、开源、支持工作流 | 产品经理/开发者 |
| **Coze（扣子）** | 零代码平台 | 字节出品、插件丰富、免费 | 非技术人员 |
| **FastGPT** | 开源平台 | 国内团队、中文优化好 | 国内用户 |

**选择建议：**
- 快速验证想法 → Coze / Dify
- 生产级应用 → LangChain + 自研
- 已有数据系统 → LlamaIndex

## 三、LangChain 与 LlamaIndex

### 3.1 LangChain

**定位：** AI 应用的"胶水框架"，把各种组件串起来。

**核心概念：**

| 概念 | 作用 | 类比 |
|------|------|------|
| **Chain** | 把多个步骤串成流水线 | 工厂流水线 |
| **Prompt Template** | 可复用的 Prompt 模板 | Word 模板 |
| **Memory** | 记住对话历史 | 记事本 |
| **Tool** | 外部工具/API | 工具箱 |
| **Agent** | 自主决策的执行器 | 智能助理 |

**一个简单的 LangChain Chain：**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

# 定义模板
template = """
你是一位{role}，请用{style}的风格回答以下问题：
{question}
"""
prompt = ChatPromptTemplate.from_template(template)

# 创建 Chain
llm = ChatOpenAI(model="gpt-5", temperature=0.7)
chain = prompt | llm

# 执行
result = chain.invoke({
    "role": "资深程序员",
    "style": "通俗易懂",
    "question": "什么是递归？"
})
print(result.content)
```

**LangChain 的优缺点：**

| 优点 | 缺点 |
|------|------|
| 生态最丰富，社区活跃 | 版本迭代快，API 经常变 |
| 抽象层次合理，易上手 | 过度封装，复杂场景受限 |
| 与各种模型/API 集成好 | 生产环境需要大量调优 |

### 3.2 LlamaIndex

**定位：** 专注“数据 + LLM”的连接，尤其适合 RAG 场景；它并非唯一选择。

**核心概念：**

| 概念 | 作用 |
|------|------|
| **Index** | 数据索引（向量索引、树形索引等） |
| **Retriever** | 从索引中检索相关内容 |
| **Query Engine** | 检索 + 生成的一体化查询 |
| **Data Connector** | 连接各种数据源（PDF、数据库、API） |

**LlamaIndex vs LangChain：**

| 维度 | LlamaIndex | LangChain |
|------|-----------|-----------|
| **专注点** | 数据连接与检索 | 通用 AI 应用编排 |
| **RAG 能力** | 数据连接与索引能力更突出 | 可通过组件组合实现 |
| **Agent 能力** | 也支持工作流与 Agent | 通用编排能力更突出 |
| **上手难度** | 中等 | 较简单 |
| **最佳场景** | 知识库问答 | 多步骤工作流 |

**实践建议：**
- 数据连接和索引是重点 → 优先评估 LlamaIndex
- 通用编排是重点 → 优先评估 LangChain
- 两者可以混用（LlamaIndex 做检索，LangChain 做编排）

## 四、向量数据库（Vector DB）

### 4.1 为什么需要向量数据库？

传统数据库常见的是精确查询和全文检索；要做语义检索，则需要 Embedding 与向量索引。

向量数据库按**语义**搜索（搜"猫"还能找到"kitten"、"喵星人"、"橘橘"）。

**原理：** 把文字转换成 Embedding 向量，计算向量之间的距离，距离越近语义越相似。

### 4.2 常用向量数据库对比

| 数据库 | 部署方式 | 特点 | 适用场景 |
|--------|---------|------|---------|
| **Chroma** | 本地/嵌入式 | 轻量、零配置、Python 原生 | 快速原型、个人项目 |
| **Pinecone** | 托管 SaaS | 无需运维、自动扩缩容 | 生产环境、团队协作 |
| **Milvus/Zilliz** | 本地/云托管 | 开源、高性能、分布式 | 大规模企业应用 |
| **pgvector** | PostgreSQL 插件 | 与 SQL 数据库一体 | 已有 PostgreSQL 的项目 |
| **Weaviate** | 本地/云 | 模块化、GraphQL 接口 | 需要复杂查询的场景 |
| **Qdrant** | 本地/云 | Rust 编写、高性能 | 高并发场景 |

### 4.3 选型建议

```
个人项目/快速验证    → Chroma（pip install chromadb，5 行代码）
已有 PostgreSQL      → pgvector（加一个扩展即可）
生产环境不想运维     → Pinecone（按量付费，零运维）
大规模/高并发        → Milvus / Qdrant
需要复杂过滤条件     → Weaviate
```

### 4.4 关键参数

| 参数 | 说明 | 建议值 |
|------|------|--------|
| **维度（Dimension）** | 向量的长度，由 Embedding 模型决定 | 768（BERT）/ 1536（OpenAI）/ 1024（国产模型） |
| **距离度量** | 计算向量相似度的方式 | Cosine（通用）/ Euclidean（数值特征）/ Dot（归一化后） |
| **索引类型** | 加速检索的数据结构 | HNSW（平衡速度和精度）/ IVF（大规模数据） |

## 五、AI Agent 框架

### 5.1 什么是 AI Agent？

普通 AI 是"问答机"：你问一句，它答一句。

Agent 是面向目标的多步工作流：它会根据中间结果决定下一步。单次工具调用不等于 Agent。

**核心能力：**

1. **规划（Planning）**：把大目标拆成小步骤
2. **状态管理**：保存必要的上下文和中间结果
3. **工具调用（Tool Use）**：在授权范围内请求外部 API
4. **评估或校验**：在需要时检查结果并调整下一步

### 5.2 Agent 执行循环

```
用户输入目标
    ↓
Agent 规划：拆分成步骤
    ↓
执行步骤 1 → 调用工具 / 生成内容
    ↓
观察结果
    ↓
反思：结果对吗？需要调整吗？
    ↓
执行步骤 2 → ...
    ↓
（循环直到完成或达到最大步数）
    ↓
输出最终结果
```

### 5.3 主流 Agent 框架

| 框架 | 特点 | 适用场景 |
|------|------|---------|
| **LangChain Agent** | 生态丰富、集成好 | 通用 Agent 开发 |
| **AutoGPT** | 全自动、目标驱动 | 实验性项目 |
| **MetaGPT** | 多 Agent 协作、模拟软件公司 | 复杂项目开发 |
| **CrewAI** | 多角色协作、易用 | 团队任务自动化 |
| **Dify Agent** | 可视化、低代码 | 快速搭建 |
| **Coze Agent** | 零代码、插件多 | 非技术人员 |

### 5.4 ReAct 模式（Reasoning + Acting）

最流行的 Agent 设计模式，让 AI "边想边做"。

**例子：**

```
用户："北京今天天气怎么样？适合穿什么？"

Agent 思考 1：用户问天气和穿衣建议，我需要先查天气。
Agent 行动 1：调用 weather_api(city="北京")
Agent 观察 1：返回 "晴，25°C，微风"

Agent 思考 2：25度晴天，适合穿短袖。但早晚可能凉，建议带件薄外套。
Agent 行动 2：生成回答
Agent 观察 2：回答已生成

最终输出："北京今天晴天，25度，微风。建议穿短袖+薄外套，早晚温差注意保暖。"
```

## 六、模型部署方式

### 6.1 四种部署方式

| 方式 | 成本 | 难度 | 数据隐私 | 延迟 | 适合场景 |
|------|------|------|---------|------|---------|
| **调用 API** | 按量付费 | 极低 | 低 | 中 | 大多数应用 |
| **云端部署** | 中等 | 中等 | 中 | 低 | 需要数据不出域 |
| **本地部署** | 硬件成本 | 较高 | 高 | 低 | 完全离线、敏感数据 |
| **边缘部署** | 硬件成本 | 高 | 高 | 极低 | 手机、IoT 设备 |

### 6.2 API 调用（最常用）

```python
from openai import OpenAI

client = OpenAI()
response = client.responses.create(
    model="gpt-5",
    input="你好"
)
print(response.output_text)
```

**主流 API 提供商：**

| 提供商 | 代表模型 | 特点 |
|--------|---------|------|
| OpenAI | GPT-4 / GPT-3.5 | 最强通用能力 |
| Anthropic | Claude | 长文本、安全性 |
| 百度 | 文心一言 | 中文优化 |
| 阿里 | 通义千问 | 性价比高 |
| 智谱 | ChatGLM | 开源友好 |
| DeepSeek | DeepSeek-V2 | 极低成本 |

### 6.3 本地部署工具

| 工具 | 特点 | 适用 |
|------|------|------|
| **Ollama** | 一行命令运行模型，最简单 | 个人使用 |
| **LM Studio** | 图形界面，友好 | 非技术人员 |
| **llama.cpp** | 性能最好，支持各种量化 | 开发者 |
| **vLLM** | 高吞吐 API 服务 | 生产环境 |
| **Text Generation Inference** | HuggingFace 出品 | 企业部署 |

**Ollama 示例：**

```bash
# 安装 Ollama
# macOS: brew install ollama

# 下载并运行模型
ollama run llama3

# 模型自动下载到本地，之后断网也能用
```

### 6.4 模型量化

大模型文件很大，普通电脑跑不动。**量化**就是用精度换空间。

| 精度 | 文件大小（以 7B 模型为例） | 效果 | 适用 |
|------|------------------------|------|------|
| FP16（原始） | 14 GB | 最好 | 高端显卡 |
| INT8 | 7 GB | 很好 | 中高端显卡 |
| INT4 | 3.5 GB | 较好 | 消费级显卡 |
| INT2 | 1.8 GB | 一般 | 勉强能跑 |

**量化格式：**
- **GGUF**：llama.cpp 专用，社区最丰富
- **GPTQ**：适合 GPU 推理
- **AWQ**：比 GPTQ 更快，质量更好
- **GGML**：GGUF 的前身，已逐步淘汰

## 七、模型评估指标

### 7.1 为什么要评估？

AI 模型的输出不像传统软件有"对/错"，需要专门的评估方法。

### 7.2 自动评估指标

#### BLEU（Bilingual Evaluation Understudy）

**用途：** 评估生成文本与参考文本的相似度，常用于机器翻译、文本生成。

**原理：** 统计生成文本中有多少 n-gram（连续的 n 个词）出现在参考文本中。

**缺点：** 只看重合度，不理解语义（"猫抓了老鼠"和"老鼠被猫抓了"意思一样，但 BLEU 得分低）。

#### ROUGE（Recall-Oriented Understudy for Gisting Evaluation）

**用途：** 评估摘要质量，常用于文本摘要任务。

**原理：** 统计参考摘要中有多少词出现在生成摘要中（侧重召回率）。

**变体：**
- ROUGE-1：单个词的重合
- ROUGE-2：两个词的重合
- ROUGE-L：最长公共子序列

### 7.3 人工评估

自动指标有局限，**人工评估仍是金标准**。

**常用维度：**

| 维度 | 评估内容 |
|------|---------|
| **准确性** | 事实是否正确 |
| **流畅性** | 读起来是否自然 |
| **相关性** | 是否回答了问题 |
| **完整性** | 是否覆盖了所有要点 |
| **安全性** | 是否有害、偏见、泄露隐私 |

**评估方法：**
- **A/B 测试**：同一问题，两个模型回答，人工选更好的
- **Likert 量表**：1-5 分打分
- **成对比较**：两两对比，排出优劣

### 7.4 LLM-as-a-Judge

**新趋势：** 用 GPT-4 等强模型来评估其他模型的输出。

**优点：**
- 比人工快、成本低
- 评估标准一致

**缺点：**
- 强模型也有偏见
- 对创意类任务评估不准

**实践建议：**
- 先用自动指标快速筛选
- 再用 LLM-as-a-Judge 细评
- 最后用人工评估关键样本

## 八、小结

一张图看懂 AI 工程工具链：

```
用户提问
    ↓
[Prompt Engineering] 结构化提问、角色设定、Few-shot
    ↓
[RAG 系统]
    ├── 文档切分（Chunking）
    ├── 向量数据库（Chroma/Pinecone/Milvus）
    ├── 检索（关键词 + 语义）
    └── 生成回答（带引用标注）
    ↓
[AI Agent]
    ├── 规划（拆步骤）
    ├── 记忆（上下文）
    ├── 工具调用（API/搜索/计算）
    └── 反思（检查修正）
    ↓
[模型层]
    ├── API 调用（OpenAI/Claude/国产）
    ├── 本地部署（Ollama/llama.cpp）
    └── 量化（GGUF/GPTQ/AWQ）
    ↓
[评估]
    ├── 自动指标（BLEU/ROUGE）
    ├── LLM-as-a-Judge
```
